# HOYANG inquiry email Worker

This standalone Cloudflare Worker receives the statically hosted HOYANG contact
form as `multipart/form-data`, validates the inquiry and optional images, and
sends one internal email through the Resend Email API. Images are attached to
the email; they are not published or stored by the website.

The public endpoint is `POST /inquiry`. The Worker also handles CORS preflight
at `OPTIONS /inquiry`. Every other path returns `404`, and unsupported methods
return `405`.

## Configuration

Non-secret Worker variables are committed in `wrangler.jsonc`:

- `ALLOWED_ORIGINS` — comma-separated exact origins permitted to submit.
- `INQUIRY_FROM_EMAIL` — the verified Resend sender.

Required Worker secrets are never public frontend or GitHub repository
variables:

- `RESEND_API_KEY`
- `INQUIRY_TO_EMAIL` — the private mailbox where HOYANG receives inquiries.

For local development, copy `.dev.vars.example` to `.dev.vars` and replace the
placeholders locally. Never commit `.dev.vars`.

## Manual Resend setup

1. Create a Resend account.
2. Add the sending subdomain `send.hoyang.co.kr` in Resend.
3. Copy the exact SPF, DKIM, and MX records generated by Resend into Gabia DNS.
4. Preserve the existing GitHub Pages A and CNAME records.
5. In Gabia, add a trailing period to DNS destination values when Gabia
   requires a fully qualified domain name.
6. Wait until Resend marks the sending domain as verified.
7. Create a sending-only Resend API key.
8. After verification, use
   `HOYANG 문의 <inquiry@send.hoyang.co.kr>` as the sender.

Do not copy DNS values from an example or another account. Resend generates
account- and region-specific records.

This first version sends only the internal inquiry email. It intentionally does
not send a customer confirmation email, so the public form cannot be used as an
email-sending relay.

## Manual Cloudflare setup and deployment

Run:

```bash
cd workers/inquiry-email
npm install
npx wrangler login
npx wrangler secret put RESEND_API_KEY
npx wrangler secret put INQUIRY_TO_EMAIL
npm run typecheck
npm run test
npm run deploy:dry
npm run deploy
```

Enter the private destination mailbox when Wrangler prompts for
`INQUIRY_TO_EMAIL`. Do not place that address in frontend code, committed files,
GitHub repository variables, or any variable beginning with `NEXT_PUBLIC_`.

After deployment, record the generated endpoint in this form:

```text
https://hoyang-inquiry-email.<account-subdomain>.workers.dev/inquiry
```

Use the actual account subdomain printed by Wrangler; do not guess or hardcode
it.

## Connect the GitHub Pages site

In GitHub, open:

```text
Repository
→ Settings
→ Secrets and variables
→ Actions
→ Variables
```

Add this public build-time configuration:

```text
Name:
NEXT_PUBLIC_INQUIRY_ENDPOINT

Value:
https://<deployed-worker-host>/inquiry
```

The endpoint URL is public configuration, not a secret. The Pages workflow in
`.github/workflows/deploy-pages.yml` passes it to the Next.js build as
`${{ vars.NEXT_PUBLIC_INQUIRY_ENDPOINT }}` while preserving
`NEXT_PUBLIC_NAVER_MAP_CLIENT_ID`, `NEXT_PUBLIC_SITE_URL`, and
`NEXT_PUBLIC_SITE_RELEASE_MODE`. Rerun the GitHub Pages deployment after adding
or changing the variable.

Keep the main website on GitHub Pages. Do not add a Next.js API route or expose
the Resend API key, recipient address, or another secret to the static build.

## Privacy-policy launch guard

The contact form remains enabled only when both conditions are true:

```ts
endpointValid && siteConfig.legal.privacyPolicyStatus === "final";
```

This Worker setup does not change `privacyPolicyStatus` to `final`. Before
enabling production submissions, the site owner and appropriate legal reviewer
must separately review and finalize the actual privacy policy. It should
disclose:

- customer contact information collected;
- purchase information collected;
- optional photo attachments;
- the purpose of collection;
- the retention period;
- email delivery and third-party processors; and
- how deletion requests are handled.

## Post-deployment verification

After the Worker and Pages build are deployed, manually test:

1. An inquiry without images.
2. One JPG, one PNG, and one WebP in separate submissions.
3. Three valid images together.
4. Four images.
5. A file larger than 5 MB.
6. A renamed non-image file.
7. Mobile photo selection.
8. Drag-and-drop.
9. Removing a preview.
10. Retrying after a simulated endpoint failure.
11. Replying to the received email and confirming it addresses the customer.
12. Opening each received image attachment.
13. A request from a disallowed origin.
14. A honeypot request.
15. Repeating the same submission ID.

Confirm that every submitted detail appears in the internal email, no image is
publicly hosted, no API key is present in built JavaScript, and the browser uses
multipart form data. Confirm exact-origin CORS, preserved files after a failed
submission, cleared files after success, and a disabled form until the privacy
policy is final.
